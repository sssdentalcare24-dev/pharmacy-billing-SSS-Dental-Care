What changed and why

apps-script/Code.gs (v3, rewritten around the old functions)

  • Login/session (login_, getSession_, changePassword_, users): salted SHA-256 ×500 hashes in a Users tab; random 64-char session tokens in CacheService; 3 h idle / 12 h absolute expiry; 5 wrong passwords → 15 min lock; password rules; owner can create/reset/disable logins; disabling or resetting ends that user's sessions; emergencyResetOwnerPassword for recovery. Why: S-01…S-03, S-06.
  • handle_ gatekeeper: every request must be POST with a valid session; per-action role table (PERMS); staff never receive cost prices, purchases or expenses; writes run under a lock and are de-duplicated by request ID; denials and rejections audited. Why: S-02, S-04, S-05.
  • saveBill_: re-validates every line, totals, discount limit, payment split; FEFO batch allocation; cost of goods from the actual batches; sequential bill number; shortfalls recorded instead of hidden. Why: B-05…B-07, B-18, B-19.
  • cancelBill_ / cancelPurchase_ replace deletion; stock restored to the exact batches; reason required. Why: B-09.
  • Batches + StockMovements: addPurchase_ creates batches (batch no, expiry, free qty, MRP, invoice no, duplicate-invoice check); adjustStock_ (damaged, expired, returns, count corrections — reason required); updateMedicine_ cannot change stock silently; deleteMedicine_ → Inactive.
  • Clinic records: server receipt numbers (reserveReceiptNo_); record IDs for prescriptions/exams/receipts; soft deletes; same-doctor appointment clash check. Why: B-10, B-11, B-15, B-16.
  • Backups: backupNow_ (verified), scheduledBackup (daily/weekly/monthly + pruning + failure e-mail), restoreFromBackup, installTriggers.
  • Migration: migrateToV3DryRun, migrateToV3 (backup first, additive, re-runnable), validateData_.

Deployment — GitHub Pages + the same Apps Script

GitHub repo (main) ──► GitHub Pages  https://sssdentalcare24-dev.github.io/pharmacy-billing-SSS-Dental-Care/
Apps Script (the existing project, same /exec link) ──► the existing spreadsheet

No Netlify, no second Apps Script, no second spreadsheet. Safety comes from the automatic verified backup that migrateToV3 makes before it changes anything, and from the fact that the upgrade only adds tabs and columns.

The website and the Apps Script must be on the same version: the v3 app talks only to the v3 server. Until the server is updated, the new app shows a red banner: "The Apps Script server has not been updated yet…" — nothing is saved in the meantime.

A. Switch-over (≈15 minutes, do it when the clinic is quiet)

  1. Apps Script editor → open your existing project.
  2. Project settings → set Time zone = (GMT+05:30) India Standard Time (optional: tick Show "appsscript.json" and paste apps-script/appsscript.json).
  3. Open Code.gs → select all → paste the new apps-script/Code.gs from GitHub → Save.
  4. Function menu → migrateToV3DryRun → Run → read the log (it only lists what will be added).
  5. Function menu → migrateToV3 → Run → allow the permissions Google asks for (Drive for the backup, Gmail for e-mails).
  6. The log shows "Backup OK" with a link, then "✅ Migration complete".
  7. It also shows the temporary passwords for owner and staff (also e-mailed to the clinic Google account).
  8. Function menu → installTriggers → Run (daily backup ~2 AM + daily stock e-mail ~8 AM).
  9. Deploy → Manage deployments → ✏️ Edit → Version: New version → Deploy. The /exec link stays the same.
  10. Open the app on each device → log in with the temporary password → choose a personal password (at least 8 characters).
  11. Owner: Settings → set the staff discount limit, check Backups shows a verified backup, glance at the Audit log.

If the browser still shows the old app: close and reopen it (the app updates itself in the background).

B. Quick check after switching (5 minutes)

  • ☐ Owner and staff can log in; staff sees only the staff pages
  • ☐ Make a small bill → "✅ Saved on server · Bill No SSDC-…"; stock goes down
  • ☐ Owner → All Bills → ✖ cancel that test bill with reason "test" → stock comes back
  • ☐ Inventory → 📦 Stock on one medicine shows its batch (OPENING)
  • ☐ Settings → Backups → ✅ verified · Audit log shows the logins and the test bill
  • ☐ Thermal printer still prints

C. If something is wrong — rollback

  1. Apps Script → Deploy → Manage deployments → ✏️ Edit → Version: choose the previous version → Deploy.
  2. GitHub → the repository → Commits → revert to commit 9a392c4 (the version before v3), or ask Claude to do it.
  3. Data: nothing was removed. If needed, open Drive → SSDC Backups → SSDC Backup pre-migration … and run restoreFromBackup("<file id>") (see MIGRATION.md §8).

D. Forgotten passwords

  • Staff: owner → Settings → Users → Reset password (temporary password, staff changes it at next login).
  • Owner: Apps Script editor → run emergencyResetOwnerPassword → a temporary password is e-mailed to the clinic Google account.

G. Security on GitHub Pages

GitHub Pages cannot send security headers, so index.html carries a Content-Security-Policy <meta> tag (scripts only from this site, network only to Google Apps Script, no plugins) and no-referrer. The repository is public but contains no secrets: no passwords, no hashes, no Apps Script link (entered once per device), and the server requires a login for every request.

4. Security vulnerabilities

# Sev Finding
S-01 🔴 Backend has no authentication. Anyone who has the Apps Script URL can read every patient, phone number, prescription and bill (?action=getAllData) and delete records. The URL was hard-coded in the original HTML.
S-02 🔴 Permissions are only hidden buttons. "Staff" restrictions live in the browser; any action can be called directly.
S-03 🔴 Login is checked in the browser. Since 27 Oct passwords are SHA-256 hashes, but the hashes are public and the passwords (1234, 123.456) are trivially guessable — and the check can be skipped entirely from DevTools.
S-04 🟠 Patient data travels in URL query strings (GET) — ends up in browser history, proxy and Google request logs.
S-05 🟠 No audit trail: no record of who created/deleted a bill, changed stock, etc.
S-06 🟠 No session expiry, no failed-login lockout, no password change, no account recovery.
S-07 🟡 Stored XSS: names/notes are inserted with innerHTML unescaped (84 places). Input comes from staff only, so risk is insider/accidental.
S-08 🟡 Patient data cached unencrypted in localStorage (pt_records, appointments, medistock_cache, histories) and not cleared on logout.
S-09 🟡 UPI ID + amount sent to third-party api.qrserver.com to draw QR (a local QR library is already bundled).
S-10 ⚪ No security headers (GitHub Pages can't set them) → fixed with a Content-Security-Policy <meta> tag.

8. Database limitations (Google Sheets)

  • No real relationships: bills reference medicines by ID, but patients are referenced by name text everywhere (bills, receipts, prescriptions, exams).
  • Single Medicines.Stock number and single Expiry per medicine — no batches, so FEFO and expiry-loss tracking are impossible.
  • No stock ledger: stock changes in place with no history.
  • No status columns: cancellation = deletion.
  • No server timestamps on some sheets; dates mixed between text and Date cells.
  • Sheets limits: 10 M cells per spreadsheet; Apps Script ~30 simultaneous executions, 6-min max runtime. Comfortable for one clinic for several years if data loading is paginated.

9. Mobile usability

  • Zoom disabled (user-scalable=no) — accessibility issue.
  • Medicine choice is a plain <select> — slow with many medicines on a phone; no search/barcode.
  • Tables have mobile card versions ✅. Payment button not fixed on small screens.

10. Data consistency

  • Many histories exist only on the device that created them: prescriptions, exam forms, treatment receipts, combined bills (rx_history, ef_history, tr_history, cb_history). Clearing the browser loses them locally (Sheets has partial copies).
  • Optimistic saves show "saved" before the server confirms; failures only show a toast.
  • Two devices billing the same medicine at the same time each check stale stock.

Until the migration has run, the new server refuses every request with "Server update not finished" — the app never writes into a half-migrated sheet.

5. Duplicate detection

  • Bills: same Bill ID → stored once (retries, double taps, offline re-sends).
  • Every write carries a request ID; the server replays the original answer for 6 h.
  • Purchases: same ID → once; same invoice no + medicine + batch → refused.
  • Medicines: same name (case-insensitive) → existing one returned.
  • Treatment receipts / prescriptions / exam forms: same Record ID → once.
  • Appointments: same doctor + date + time → refused (unless explicitly allowed).

6. Data validation

Server-side on every write: positive whole quantities, prices ≥ 0, line = qty × price, subtotal = Σ lines, discount ≤ subtotal and ≤ staff limit, total = subtotal − discount, split amounts = total, known medicine, known payment mode, required names/dates, password strength.

7. Backup procedure

  1. Automatic (installTriggers): daily ~2 AM; Sundays also weekly; 1st of month also monthly. Kept: 14 daily, 8 weekly, 12 monthly, 30 manual. Older copies go to Drive trash (recoverable 30 days).
  2. Manual: Settings → Backups → Back up now, or run backupNowFromEditor.
  3. Verification: every copy is reopened and each tab's row count compared with the original. Mismatch = failure.
  4. Alerts: a failed automatic backup e-mails the clinic Google account and is written to the AuditLog.

8. Rollback procedure

Situation Steps
Undo the whole upgrade Apps Script → Deploy → Manage deployments → ✏️ edit → choose the previous version → Deploy (same link). Open the SSDC Backup pre-migration … copy in Drive if the data must also go back; run restoreFromBackup("<file id>"). Re-deploy the previous website: commit 9a392c4 (the current main).
Bad data after a mistake Drive → SSDC Backups → open the latest good copy → check it → in Apps Script run restoreFromBackup("<file id>"). The app now reads the backup; the current file is backed up first and left untouched. To undo: restoreFromBackup("<previous id>") (logged).
One wrong record Owner: cancel the bill / purchase (stock is restored), or record a stock adjustment with a reason. Nothing needs deleting.
