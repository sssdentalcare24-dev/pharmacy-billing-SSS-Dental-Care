# Stage 1 — Complete Source Code Audit

**Project:** Sri Sai Speciality Dental Care — Pharmacy Billing & Clinic Management
**Audited:** 27 Oct 2026, commit `9a392c4` (`main`)

Severity: **🔴 Critical** (data loss, wrong money, open patient data) · **🟠 High** · **🟡 Medium** · **⚪ Low**

## 1. Architecture as it exists today

```
Browser (index.html + js/app.js)  ──GET ?action=…&params──►  Google Apps Script Web App (Code.gs)
   │  localStorage: caches + device-only histories                    │
   │  Service worker: offline app shell                               ▼
   └─ Bluetooth ESC/POS thermal printer                       Google Sheets (one spreadsheet)
```

Google Sheets tabs: `Medicines`, `Bills`, `BillItems`, `Purchases`, `TreatmentReceipts`, `Prescriptions`, `Patients`, `Appointments`, `ExamForms`, `Settings`, `Expenses`.

All application logic (prices, totals, discounts, profit, stock checks, permissions) runs **in the browser**. The server stores whatever the browser sends.

## 3. Bugs and calculation errors

| # | Sev | Where | Problem | Effect |
|---|---|---|---|---|
| B-01 | 🔴 | `loadData()` catch → `loadDemoData()` | If Sheets fails to load (bad network, Apps Script error), the app **replaces real medicines with 3 demo medicines** (Amoxicillin/Ibuprofen/Paracetamol, IDs 1-3) and empties the bill list | Staff can bill fake items; bills get saved against non-existent medicine IDs; stock never deducted |
| B-02 | 🔴 | `renderTreatmentChart()` | When no local treatment data, shows **hard-coded fake numbers** (40/20/15/10/10/5) as if real | Misleading business report |
| B-03 | 🔴 | Combined bill (`04-combined-bill.js`) | Uses `window.medicines` / `window.bills`, which don't exist (`let` variables aren't on `window`) | Local stock not reduced; **cost price saved as ₹0** for every combined-bill item (profit overstated); bill doesn't appear in lists until reload; reprint-from-All-Bills falls back to device history only |
| B-04 | 🔴 | Combined bill `addCbMedicine` | `parseInt(stock) \|\| 9999` → stock 0 becomes 9999 | Out-of-stock medicines can be sold |
| B-05 | 🔴 | Backend `getAllData` | Payment mode `Split` isn't in the allowed list → read back as **Cash**; split cash/UPI amounts never sent or stored; `paymentRef` sent but not stored | Wrong payment-mode reports; no UPI reference trail |
| B-06 | 🟠 | Billing cart | Quantity can be 0, negative or blank (`NaN`); `updateCartQty` has no stock check; adding the same item twice skips the stock check | Negative line totals; overselling |
| B-07 | 🟠 | Discount | Discount % unbounded (e.g. 150% → negative bill); no staff limit | Revenue loss / errors |
| B-08 | 🟠 | Purchases | Local ID `PUR-<time>` differs from server ID `PUR-<other time>`; if a just-added medicine is chosen the **temporary medicine ID** is sent | Deleting a fresh purchase deletes nothing on server; stock not added on server |

## 4. Security vulnerabilities

| # | Sev | Finding |
|---|---|---|
| S-01 | 🔴 | **Backend has no authentication.** Anyone who has the Apps Script URL can read every patient, phone number, prescription and bill (`?action=getAllData`) and delete records. The URL was hard-coded in the original HTML. |
| S-02 | 🔴 | **Permissions are only hidden buttons.** "Staff" restrictions live in the browser; any action can be called directly. |
| S-03 | 🔴 | Login is checked in the browser. Since 27 Oct passwords are SHA-256 hashes, but the hashes are public and the passwords (`1234`, `123.456`) are trivially guessable — and the check can be skipped entirely from DevTools. |
| S-04 | 🟠 | Patient data travels in **URL query strings** (GET) — ends up in browser history, proxy and Google request logs. |
| S-05 | 🟠 | No audit trail: no record of who created/deleted a bill, changed stock, etc. |
| S-06 | 🟠 | No session expiry, no failed-login lockout, no password change, no account recovery. |
| S-07 | 🟡 | Stored XSS: names/notes are inserted with `innerHTML` unescaped (84 places). Input comes from staff only, so risk is insider/accidental. |
| S-08 | 🟡 | Patient data cached unencrypted in localStorage (`pt_records`, `appointments`, `medistock_cache`, histories) and not cleared on logout. |
| S-09 | 🟡 | UPI ID + amount sent to third-party `api.qrserver.com` to draw QR (a local QR library is already bundled). |
| S-10 | ⚪ | No security headers (GitHub Pages can't set them) → fixed with a Content-Security-Policy `<meta>` tag. |

## 5. Performance (measured 27 Oct, Lighthouse 13.5 + real throttling — see README)

Already done on 27 Oct: file split → single bundle, inline CSS, 4 KB embedded logo, service worker, lazy lists, idle rendering, server-side cache. First visit 1.68 s → 0.98 s; repeat 1.68 s → 0.21 s; Lighthouse 80 → 97.

Remaining bottlenecks:
- **Every startup downloads every record** (`getAllData`: all bills, items, patients, appointments, purchases, expenses). Grows forever → will slow down month by month.
- Each request to Apps Script costs 0.5–3 s (cold start). UI does 2 calls at login (`getAllData`, `getSettings`).
- `updateMedicineSelect` rebuilds 3 full `<select>` lists on every refresh; no search box for medicines (scrolling a long dropdown).
- JS is not minified (440 KB raw / ~100 KB gzip).

## 8. Database limitations (Google Sheets)

- No real relationships: bills reference medicines by ID, but patients are referenced **by name text** everywhere (bills, receipts, prescriptions, exams).
- Single `Medicines.Stock` number and single `Expiry` per medicine — **no batches**, so FEFO and expiry-loss tracking are impossible.
- No stock ledger: stock changes in place with no history.
- No status columns: cancellation = deletion.
- No server timestamps on some sheets; dates mixed between text and Date cells.
- Sheets limits: 10 M cells per spreadsheet; Apps Script ~30 simultaneous executions, 6-min max runtime. Comfortable for one clinic for several years if data loading is paginated.

## 9. Mobile usability

- Zoom disabled (`user-scalable=no`) — accessibility issue.
- Medicine choice is a plain `<select>` — slow with many medicines on a phone; no search/barcode.
- Tables have mobile card versions ✅. Payment button not fixed on small screens.

## 10. Data consistency

- Many histories exist **only on the device** that created them: prescriptions, exam forms, treatment receipts, combined bills (`rx_history`, `ef_history`, `tr_history`, `cb_history`). Clearing the browser loses them locally (Sheets has partial copies).
- Optimistic saves show "saved" before the server confirms; failures only show a toast.
- Two devices billing the same medicine at the same time each check stale stock.

## 12. Architecture decision: Firebase vs. Google Sheets

| | Keep Google Sheets + Apps Script (hardened) | Migrate to Firebase Auth + Firestore |
|---|---|---|
| Existing data & staff habits | Unchanged; owner keeps viewing/exporting Sheets | Full migration + sync back to Sheets for reports |
| Server-side auth & RBAC | Yes — sessions, roles, lockout implemented in Apps Script | Yes — Firebase Auth + security rules |
| Cost | Free | Free tier likely enough; billing account required |
| Speed | 0.5–3 s per call (mitigated by cache) | ~100–300 ms |
| Risk | Low, incremental | High: rewrite of every save/load path |
| Setup the owner must do | Paste script, run one migration | Create Firebase project, keys, rules, hosting config |

**Decision: keep Google Sheets + Apps Script, hardened.** It satisfies the security requirements (server-side auth, server-side permission checks, POST bodies, audit log) without risking the clinic's data or daily work. Firestore remains a documented future option (`docs/MIGRATION.md`) if speed or scale ever becomes the limit.
